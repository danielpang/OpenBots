## Trust boundaries

From most to least trusted (plan 17):

1. **Server core:** the master key, provider keys and the database.
2. **MCP servers:** vendor code with its own secrets only.
3. **The computer sandbox:** arbitrary code, no secrets, no internal network, resource caps.
4. **Webhook payloads, fetched pages and other Bots' messages:** data, never instructions.
5. **Model output:** every side effect passes the policy gate.

The review found that boundary 2 did not hold. MCP stdio servers run inside the server core's container, as the server's own user in the default image, and any member could add a custom command (S-1). Since 8.4a only admins can add a custom command, only once an admin turns it on, and catalog servers are confined (S-1, S-3, fixed). Stdio servers still share the server's container, but since 8.4b the compose service gives the server CAP_SETUID and CAP_SETGID, so each runs as `nobody` with no capabilities, and the server is non-dumpable (S-1). On the managed service they no longer run on the server at all: each runs in its owner's computer (`OPENBOTS_STDIO_RUNNER=computer`, below). Boundary 3 holds against the database and the Docker API. Inside one computer, each Bot's screen now runs as its own user behind an X cookie, so one Bot's commands cannot reach another Bot's screen (S-7, fixed, needs Docker verification).

### 1. Encrypted secrets

**What exists**

- AES-256-GCM envelope `[v][kid][nonce][tag][ct]`, with the header bound as AAD and a keyring for rotation (`apps/server/src/secrets.ts`). `kid` is one byte of an HMAC under the key that sealed it (`keyId`), so operators never number keys; envelopes from before key ids carry kid 1 and still open.
- **Master key rotation (plan 4.9, 8.4b).** `OPENBOTS_MASTER_KEY` seals, and the keys in `OPENBOTS_MASTER_KEY_PREVIOUS` (comma-separated) only open (`keyringFromConfig`, `openEnvelope`). `rotateMasterKey` (`apps/server/src/rotation.ts`) re-seals every column in `SEALED_COLUMNS` and the sign-in OAuth tokens better-auth encrypted under the old derived secret. It walks each table in id order a batch at a time and updates a row only if it still holds the value it read, so it is safe to stop, to rerun and to run twice at once, and never overwrites a secret saved meanwhile. A worker that starts with previous keys runs it in the background; `docker compose run --rm openbots rotate-key` runs it in the foreground with progress and exits 1 while any secret opens with no configured key. Each leftover is reported by column and id and left as it is. The README's "Rotating the master key" has the steps.
- **Rotation signs everyone out.** better-auth's signing secret is HKDF-derived from the master key (`authSecret` in `auth.ts`), and better-auth checks session cookies against its current secret only: its `secrets` list (1.7) covers data it encrypts, not cookie signatures. So when the server restarts with a new key every session ends, as do email links and OAuth sign-ins in flight. API keys, invites and webhook tokens are plain hashes, and webhook and subscription signing secrets are sealed values that rotation re-seals unchanged, so all of these keep working. A separate session secret could avoid the sign-out, but not through another derivation from the master key: anything derived from the new key changes with it, and deriving from the old one would keep the old key needed forever. It would take an independent root, either a random value sealed in the database (a migration, and rotation would re-seal the same session secret) or an optional `OPENBOTS_AUTH_SECRET` variable (one more secret to keep and back up). Both are small, but both keep sessions signed with a secret that may have leaked with the master key, and a suspected leak is the main reason to rotate. Ending every session is the safer default, so 8.4b keeps the derivation; an optional `OPENBOTS_AUTH_SECRET` for scheduled rotations is a possible follow-up.
- **Secrets from files (S-1, 8.4b).** Every secret variable may be given as `NAME_FILE` instead (`SECRET_ENV_VARS` in `apps/server/src/env-files.ts`); setting both is refused. The compose service needs no change to `.env`: `docker/entrypoint.sh` writes the secrets into a 0700 tmpfs at `/run/openbots` (0600 files, uid 1000) and starts node with only their paths, so the server's `/proc/<pid>/environ`, and any child given an inherited environment, holds none of them. The server logs a warning naming each secret it found in its environment. Compose's own `secrets:` were not used: one sourced from an environment variable is mounted root-owned with mode 0400 whatever `uid` and `mode` ask (checked in a container), so uid 1000 could not read it, and an unset source variable stops the whole stack, which rules out optional ones like `OPENBOTS_MASTER_KEY_PREVIOUS`.
- Sealed columns:
  - `providers.secrets` and `providers.header_secrets`, opened only in `apps/server/src/services/providers.ts`.
  - `connectors.secrets`, which holds connector secrets, MCP OAuth tokens, and email and GitHub credentials (`apps/server/src/services/connectors.ts:126-132`).
  - The webhook signing secret (`apps/server/src/hooks/endpoints.ts:147`).
  - The outbound subscription secret (`apps/server/src/hooks/outbound.ts:114`).
  - The computer agent token (`apps/server/src/services/computer.ts:180`).
- Webhook tokens, invites and API keys are stored as hashes.
- Responses carry `hasKey`, `hasSecret` or secret names only. Tokens are shown once. A provider also carries `keyHint`, the vendor prefix and last four characters, shown to admins (and to the owner of an account provider) so they can tell keys apart, as in `sk-ant-…a1b2`: a prefix from the allowlist of vendor prefixes (`KEY_PREFIXES`; any other key shows none, since its leading characters may be secret), "…", and the last 4. Never more than half of a key is kept: a key under 20 characters, or one whose prefix and last 4 would pass half, shows only "…" and the last 2, and a key under 8 characters shows nothing. Members get `hasKey` only. It is stored in plain text in `providers.key_hint` when the key is saved or seeded from `.env`, and recomputed for every row at start-up by `backfillProviderKeyHints` (`services/providers.ts`), which logs nothing about the key. Connector secrets have no hint.

**Tests**

- `apps/server/src/secrets.test.ts`: "never stores the plaintext", "detects tampering…", and the rotation test.
- `apps/server/src/routes/connectors.test.ts`: "never returns a secret value in any response".
- `apps/server/src/routes/providers.test.ts`: "…never returning the key".
- `apps/server/src/services/providers.test.ts`: "keeps a known vendor prefix and the last four characters (P3)", "drops a prefix it does not know, whose characters may be secret", "never shows more than half of a key" and "fills and rewrites stored hints at start-up, logging nothing about the keys (P3)"; `apps/server/src/routes/providers.test.ts`: "shows a key's hint to admins, and to the owner of an account provider (P3)".

### 2. Approvals

**What exists**

- Every model tool call goes through `gated()` (`packages/agent/src/gated.ts:78-84`). The one ungated path runs an already-approved call once (`apps/server/src/workers/runs.ts:339-344`).
- Safe defaults (`packages/agent/src/policy/rules.ts:59-118`):
  - `ask` for bash, file writes, `send_email`, non-GET `http_request`, unknown tools, and connector tools without hints.
  - `auto` for reads and screen actions.
- Trigger overrides can only make a decision stricter (`packages/agent/src/policy/engine.ts:29-62`).
- Webhook runs, and runs other Bots start (a `bot_dm` run or a Bot's @mention; the floor follows who wrote the message, `runSource` in `apps/server/src/services/policy.ts`), default to `ask` (`DEFAULT_TOOL_POLICY` in `packages/shared/src/policy.ts`), plus the endpoint's override (`apps/server/src/services/policy.ts`). Owner trigger entries are merged over the defaults key by key, so only an explicit `default` lifts one.
- Webhook runs ask before a GET fetch (`web_fetch`, GET `http_request`) from a host outside the Bot's domain allowlist (`packages/agent/src/policy/engine.ts`).
- MCP read-only hints count only for catalog connectors (`connectors.catalog_id`) and connectors an admin marked trusted (`connectors.trusted`, default false); other connectors' tools ask (`packages/agent/src/policy/rules.ts`, `apps/server/src/services/policy.ts`). Only an admin sets the flag, through `PUT /connectors/{id}/trusted` (403 for members, owners included) or the "trust its read-only hints" switch in a custom connector's tool list on the Connectors page. Each change is audited as `connector.trust`, and changing the connector's command or URL clears it.
- Denials are audited.

**Tests**

- `packages/shared/src/policy.test.ts`: "merges trigger overrides deeply, keeping the default unless the owner sets one".
- `apps/server/src/services/policy.test.ts`: "asks before tools that change something in a run another Bot started", "asks before a GET fetch off the allowlist in a Routine run a webhook started", and the catalog and trusted cases in the connector test.
- `apps/server/src/workers/approvals.test.ts`: the pause, restart and resume test.
- `apps/server/src/hooks/ingress.test.ts`: "runs under the endpoint override and the stricter webhook default", and "holds a Routine run a webhook started to the webhook default too" (new).

**Gaps**

- **S-4 (fixed here):** a Routine run started by a webhook delivery had trigger `routine` (`services/routines.ts:389`), so the webhook floor did not apply. `services/policy.ts` now evaluates such runs under the webhook trigger rules.
- **S-10 (fixed here):** runs started by other Bots (`bot_message`, `bot_dm`) had no stricter default, although P2 counts other Bots' messages as data. They now ask before anything that can change something, like webhook runs. `web_fetch` and GET `http_request` stayed `auto` in webhook runs, which let injected content exfiltrate through query strings; they now ask unless the host is on the Bot's allowlist.

### 3. Per-Bot domain allowlists

**What exists**

- `hostAllowed` is checked before the request (`packages/agent/src/tools/builtin.ts`), and again on every redirect hop of `web_fetch` and `http_request` (`guardedFetch` in `apps/server/src/builtins/net.ts`). `web_fetch` honours the allowlist too.
- Private, loopback, link-local, CGNAT and other non-public ranges are blocked (`isPublicAddress` in `net.ts`). A host the allowlist names exactly may be private; the owner named it.
- The check is made where the connection is: an undici `Agent` whose `lookup` resolves each name once, checks every answer and hands the checked addresses to the socket, so a DNS answer that changes after the check is never used (S-8). IP literals are checked in the agent's connector. Credentials are dropped when a redirect changes origin.
- The same guard (`netFetch`) carries MCP Streamable HTTP sessions, OAuth discovery, registration, token and refresh requests (`services/connectors.ts`), and requests to provider endpoints not marked local (`ProviderConfig.fetch`, `services/providers.ts`). SMTP and IMAP hosts are resolved and checked once, and the client connects to that address with the name kept for TLS (`builtins/email.ts`).
- Exemptions: `NetOptions.allowPrivateNetwork` (the built-ins' `options.net`, and `AppDeps.net` for connectors, OAuth and providers) is for tests that serve fakes on 127.0.0.1; no environment variable sets it. Provider endpoints marked local skip the guard. An HTTP connector an admin marked local (`connectors.local`, `PUT /connectors/{id}/local` or the "runs on my network" switch on the Connectors page, audited as `connector.local`, cleared when the URL changes) may reach private addresses for its MCP session and OAuth requests, still through the pinned lookup; members cannot set it, and stdio connectors get 400 `NOT_HTTP` (8.4n). Outbound event subscriptions (H6) deliver through the same guard: a URL on a private, loopback or unresolvable host is refused when the subscription is saved (400 `PRIVATE_HOST`), unless an admin marks it local (`event_subscriptions.local`, the `local` field or the "Runs on my network" box in Settings > Events, audited with the subscription, cleared when the URL changes). A local subscription's deliveries may reach private addresses, still through the pinned lookup.

**Tests:** `apps/server/src/builtins/builtins.test.ts`: "keeps built-ins off private networks unless allowed", "connects to the address it checked when DNS rebinds (S-8)", "refuses a redirect to a private host or off the allowlist (S-8)", "holds web_fetch to the allowlist too (S-8)", "refuses http_request hosts outside the allowlist…", and the SMTP case. `routes/connectors.test.ts`: "keeps MCP sessions, OAuth discovery and token requests off private networks (S-8)", and "HTTP servers on the admin network (S-8)" (refused without the local mark and reached with it, admin-only, OAuth, and the pinned lookup still used). `routes/providers.test.ts`: "refuses private base URLs unless the endpoint is marked local (S-12)", "drops the stored key when the base URL moves to another host (S-12)", "drops the extra headers when the base URL moves to another host (S-12)". `hooks/outbound.test.ts`: "refuses a private receiver unless an admin marks it local (S-8)".

**Gaps**

- **S-8 (fixed in 8.4f).** The address was checked with one lookup and `fetch` resolved the name again (DNS rebinding); the allowlist was not re-checked on redirects; `web_fetch` ignored it; MCP HTTP, OAuth and mail hosts had no address check. All four now go through the guard above.
- **S-12 (fixed in 8.4f, 8.4n).** Provider base URLs had no address check, and changing one kept the stored key and the sealed extra headers. See the providers row under "Other checks".
- A local MCP server over HTTP (on the host or the compose network) is now refused; there is no per-connector "local" mark like the providers'. Run it as a stdio server, or put it behind a public name.
- The Postgres catalog server connects by itself, outside the guard (S-3).

### 4. Sandbox network separation

**What exists**

- `docker-api` is an internal network holding only the server and the proxy.
- `openbots-sbx` holds neither Postgres nor Redis (`docker/docker-compose.yml:118-125`).
- The container (`containerSpec` in `packages/computer/src/docker.ts`):
  - Not privileged. It starts as root with `CapDrop: ALL` and only `CHOWN`, `SETUID` and `SETGID` added back, under `no-new-privileges`. The agent drops to uid 1000 before it listens (S-7, below).
  - Read-only root filesystem. Two named volumes, the home and the agent's state, and no binds or published ports.
  - Memory, PID and CPU limits, and an allowlisted environment without the agent token.

**Tests:** `packages/computer/src/docker.test.ts`: "shares no compose network with Postgres, Redis or the socket proxy", "gets no provider keys or server secrets in its environment", "keeps the agent token out of its environment (S-7)".

**Gaps**

- **S-7 (fixed in 8.4c, 8.4j and 8.4m, needs Docker verification).** In 8.4c the agent stopped passing `OPENBOTS_AGENT_TOKEN` to the programs it starts: `childEnv` (`apps/computer-agent/src/config.ts`) drops it after every overlay. The container's own environment still carried the token, so `/proc/1/environ` gave it away. 8.4j removes it from the environment altogether:
  - The docker provider puts the token into the state volume as `/var/lib/openbots/token`, root's and mode 0400, through the Docker archive endpoint before each start. The docker guard allows that one archive, into that one directory, and nothing else (`packages/computer/src/token-archive.ts`, `docker-guard.ts`). The guard refuses `OPENBOTS_AGENT_TOKEN` in a create body.
  - The agent reads the file and deletes it before it listens (`takeToken` in `apps/computer-agent/src/privileges.ts`). It refuses a file that is not root's or that others may read.
  - The agent drops its effective uid to the bot user. Its real uid stays root, so the Bots' commands, which run as the bot user, cannot signal it, trace it or read its `/proc`. Changing the effective uid also makes it non-dumpable.
  - A remote agent may still take `OPENBOTS_AGENT_TOKEN` from its environment, and deletes it from `process.env` as before.
  - Tests: `packages/computer/src/docker.test.ts` "keeps the agent token out of its environment (S-7)" and "passes the token as a file in the state volume before each start, not to a running agent (S-7)". `docker-guard.test.ts` "puts only the agent token archive into a container, only into the state directory (S-7)", and the provider through the guard over HTTP. `apps/computer-agent/src/privileges.test.ts` "takeToken (S-7)" and "keeps the agent's /proc closed to the bot user's commands". The 8.4c tests still pass: `app.test.ts`, `ws.test.ts`, `screens.test.ts` and `config.test.ts` "childEnv (S-7)".
- **S-17 (fixed, needs Docker verification):**
  - The server sat on the sandbox network, so sandboxes reached its HTTP port and the unauthenticated `/metrics`. The server is still on it, at a fixed address, because it opens the agent connections; `docker/sandbox-firewall.sh` lets only the server open connections, only to port 7070, and drops the rest of the bridge traffic. `/metrics` needs `OPENBOTS_METRICS_TOKEN` (`apps/server/src/routes/health.ts`, tested in `health.test.ts`).
  - Containers on `openbots-sbx` could talk to each other. The network now has `enable_icc=false` (compose and `networkSpec`).
  - Link-local metadata, RFC 1918, CGNAT and the Docker host are dropped by the same script, which the `sandbox-firewall` service keeps applied. DNS on port 53 stays open for LAN resolvers.

### 5. Docker socket proxy

**What exists:** the `docker-guard` service in front of tecnativa/docker-socket-proxy (pinned by digest), which has `CONTAINERS`, `IMAGES`, `NETWORKS`, `VOLUMES` and `POST` on. The guard allows only the provider's requests and checks each body (`packages/computer/src/docker-guard.ts`); only the guard reaches the proxy, on the internal `docker-raw` network. Exec, build and the rest are off. It is on the internal network only, with the socket mounted read-only (`docker/docker-compose.yml:79-101`).

Volumes are a computer's only: the guard creates and reads `openbots-home-*` and `openbots-state-*` volumes alone, and since Reset computer (plan 22.14) it also passes `DELETE /volumes/{name}` for those two names and no other, with any `force` query dropped, so a volume a container still uses is never removed and the database's volume cannot be named.

**Tests:** `packages/computer/src/docker-guard.test.ts` (allowed and refused bodies and paths, "removes only computer volumes, never forced (a reset, GH5)", and the provider through the guard over HTTP); `packages/computer/src/docker.test.ts` "removes the home on a reset, and the state volume only when asked (GH5)"; `docker.test.ts` parses the compose files. CI validates them with `docker compose config`.

**Gaps**

- **S-2 (fixed, needs Docker verification):** the proxy filters by URL path only. With `CONTAINERS` plus `POST`, a `POST /containers/create` body could ask for `Privileged`, host binds or host networking, so code execution in the server container was host root. The guard now refuses those bodies.
- **S-20:** the proxy image is pinned by digest (`v0.5.0`).

### 6. Rate limits on auth and webhooks

**What exists**

- Token buckets with an atomic take: a Lua script in Redis when `REDIS_URL` is set, so every API process shares them, and in memory otherwise (`apps/server/src/infra/rate-limit.ts`).
- The client address comes from one helper, `clientIp` (`apps/server/src/client-ip.ts`). It reads `X-Forwarded-For` only when the peer is in `TRUSTED_PROXIES`, takes the right-most untrusted hop, and otherwise uses the peer. The compose stack trusts Docker's default address pool (`172.16.0.0/12`), where its tunnels run, less `172.30.0.0/16`, so a computer on the sandbox network is never a proxy.
- Auth: better-auth's `rateLimit` is configured explicitly and on in every environment, with those buckets as its storage. It keys on the address `clientIp` resolves, passed in a header `createApp` sets and overwrites (`advanced.ipAddress`). A request with no known address is refused (400 `CLIENT_IP_UNKNOWN`), not counted in a shared bucket (`apps/server/src/auth.ts`). Sign-in and sign-up keep better-auth's built-in rule of 3 per 10 s.
- Webhooks, before the body is read: 600 requests a minute per client address. After verification: the endpoint's own limit per minute, default 60, so requests that fail verification cannot spend the real sender's minute. Failed verifications have their own bucket, 10 a minute per endpoint and address (`apps/server/src/hooks/ingress.ts`). All answer 429 with `Retry-After`. The three rates are defaults: an operator sets them with `OPENBOTS_LIMITS_WEBHOOK_IP_RATE_PER_MIN`, `OPENBOTS_LIMITS_WEBHOOK_ENDPOINT_RATE_PER_MIN` and `OPENBOTS_LIMITS_WEBHOOK_FAILED_AUTH_PER_MIN`, and an admin in Settings.
- Refused deliveries in the log (H5): a request that fails the IP, token or signature check and gets past the failed-verification bucket is kept as a `refused` delivery, so an owner with a wrong Stripe or Slack secret sees why. Anyone can send one, so it keeps less than an accepted delivery: headers with the token and cookie headers removed, at most 40 of 512 characters each, a 2 KB body preview and no body file, no idempotency key, and only the 50 newest per endpoint (`recordRefusal` in `apps/server/src/hooks/endpoints.ts`). Its body never reaches a model, and it cannot be replayed (409 `NOT_REPLAYABLE`). A flood from many addresses can at most cycle those 50 rows. Requests refused before an endpoint is found (unknown handle or slug, a disabled endpoint, the size limit, the per-address bucket) are not stored.

**Tests:** `apps/server/src/infra/rate-limit.test.ts` (burst, refill, concurrent takes; Redis when `REDIS_URL` is set). `apps/server/src/http-edge.test.ts` "auth rate limit": one bucket per address, a spoofed `X-Forwarded-For` with and without a trusted proxy, and the refusal without an address. `apps/server/src/hooks/ingress.test.ts` "rate-limits verified deliveries per endpoint, failures per endpoint and address", "believes X-Forwarded-For from a trusted proxy", and "keeps a refused delivery short and only the newest, and never replays it (H5)". `apps/server/src/client-ip.test.ts`.

### 11. Pinned versions in the MCP catalog

**What exists**

- Every stdio catalog entry must carry an exact version (`packages/mcp/src/catalog.ts:48-49,88-90`).
- A catalog connector always runs the catalog's command; overriding it is refused with `PINNED` (`apps/server/src/services/connectors.ts:486-490`).
- Stdio children get a scrubbed environment (`packages/mcp/src/stdio.ts:49-55`).
- **Custom stdio is admin-only and off by default (S-1, 8.4a).** The workspace setting `customStdioEnabled` (default false, `PATCH /settings`, a switch in the Connectors page's admin section) lets admins add custom stdio servers; members never can. A member gets 403 `CUSTOM_STDIO_ADMIN_ONLY`, an admin while it is off 403 `CUSTOM_STDIO_DISABLED`, from create, import, edit and Test. The same check runs when a session starts and when a Bot's tools are listed, so existing custom stdio servers stop (and read "Disabled by admin") when the setting is off or their owner is no longer an admin (`customStdioRefusal` and `isCustomStdio` in `apps/server/src/services/connectors.ts`). A typed-in copy of a catalog package runs the catalog's pinned command, so it counts as a catalog server. A catalog stdio server gets as env only the secrets its entry declares: any other env or secret (`NODE_OPTIONS`, say) is refused with 400 `UNDECLARED_ENV` on create, import and edit, and `stdioSpawnFor` leaves out any an older row still holds.
- **A separate uid and a non-dumpable server, in the default compose install (S-1, 8.4b).** The openbots service starts as root with `cap_drop: [ALL]`, `cap_add: [SETUID, SETGID]` and `no-new-privileges` (`docker/docker-compose.yml`). Docker grants added capabilities to root only, so `docker/entrypoint.sh` then becomes uid 1000 through `setpriv --reuid=1000 --regid=1000 --clear-groups --inh-caps=-all,+setuid,+setgid --ambient-caps=-all,+setuid,+setgid --no-new-privs`: leaving uid 0 empties the permitted set, and only the two ambient capabilities survive the exec of node. With them:
  - Stdio children run as `nobody` with no capabilities at all (`launchAs` in `packages/mcp/src/privileges.ts`). Node's own `spawn({uid})` is not enough for a non-root parent: the kernel clears capabilities on a uid change only when it leaves uid 0, so the child would keep ambient CAP_SETUID and could become uid 1000. `launchAs` execs the command through `setpriv` with the inheritable and ambient sets cleared and `no_new_privs` set; without `setpriv` only a root server may switch users.
  - The server signals its children through a helper (`killCommand`): uid 1000 without CAP_KILL cannot signal `nobody` (EPERM), so closing a stdio server that ignores the end of its stdin runs `setpriv` as `nobody` with the shell's built-in `kill`. libuv can reap the child between the server's check and the helper's `kill`, and its pid could then go to another process of `nobody`, such as another connector's stdio server. So the server records the child's start time (field 22 of `/proc/<pid>/stat`) when it spawns, and the helper signals only if the pid still has that start time (`KILL_SCRIPT`, `processStartTime`); otherwise it exits 3 and signals nothing. The exit state is checked again right before each helper starts, and SIGKILL is sent only after the SIGTERM helper has finished and the grace period passed (`terminate` in `stdio.ts`), so two helpers never race. What remains is the instant between the helper's read and its `kill`, in which the child would have to be reaped and its pid handed out again, which takes a full turn of the pid space. Node has no pidfd, which would close even that.
  - At start-up the server makes itself non-dumpable (`makeNonDumpable`, called first in `main.ts`). Node has no `prctl(PR_SET_DUMPABLE)` without a native module, but the kernel resets the dumpable flag to `fs.suid_dumpable` (0 by default) whenever the effective gid changes, so switching the effective gid away and back does the same. Then `nobody` cannot read the server's `/proc/<pid>/environ` or memory, or attach to it.
  - The server runs under a 077 umask, and `protectFilesDir` (`apps/server/src/files-dir.ts`) makes `OPENBOTS_FILES_DIR` 0711 and its upload shards 0700, so `nobody` can pass through to a filesystem connector's folder and read nothing else. The secrets are in 0600 files only uid 1000 can read (above).
  - Started as uid 1000 instead (the image's `USER`, as with a plain `docker run`), the entrypoint runs as that user with no capabilities, and stdio servers run as the server's own user as before.
- **Option chosen (8.4b).** Of the three options considered (capabilities, secrets in files, a separate runner container), the first two are done together. Capabilities are what keep a child out of the server's process; files keep the values out of the server's environment and out of anything it starts with an inherited one. A runner container (plan 8, post 1.0) would also take the stdio servers off the internal networks, but it needs a new service, a transport across containers and its own image, which is more than this change could build and verify.
- **Stdio servers in the owner's computer (`OPENBOTS_STDIO_RUNNER`).** Where a stdio connector runs is set per install: `host` (the self-hosted default) as above, `computer` (the managed default) in the computer of the account that owns the connector, for the organization it belongs to. That computer is the owner's sandbox container (one per organization and owner, plan 21.3), with its firewall, egress rules and resource caps, so no two accounts or organizations share a process, a uid's view of each other, or a filesystem, and the servers have no route to the server's networks. The server asks the computer's control agent over its authenticated channel (`WS /mcp/stdio`, bearer token) to start the process, then relays MCP's stdin and stdout over that socket (`ComputerStdioHost` in `packages/mcp/src/computer-stdio.ts`, `mcpStdio` in `packages/computer/src/agent-client.ts`, `apps/computer-agent/src/mcp-stdio.ts`). The process runs as the computer's bot user in its own process group; closing the socket closes its stdin, then sends SIGTERM and SIGKILL. The connector's secrets reach it as environment variables in the start frame only: the agent passes them to `spawn`, never logs them or the arguments, and writes nothing to disk; the agent's own token is removed from the environment as for every program it starts. Catalog servers run the same pinned install as the server image, baked into the computer image from `docker/mcp-catalog`'s lockfile at `/opt/openbots/mcp` (S-20); the filesystem server's root is a folder under the computer's home, `/home/bot`, which the agent creates and refuses outside the home. Using a connector starts the owner's computer through the usual start path (status events, audit). A server that exits on its own is restarted with backoff, but never by starting a stopped computer, and stopping the computer stops its owner's servers in every process. While a server is busy the computer counts as used, so the idle sweep does not stop it mid-call. With no computer, or when it does not start, the connector shows an error and its message; it never falls back to the host. The managed service refuses `host` at start unless the operator sets `OPENBOTS_ALLOW_HOST_STDIO=1`, and then warns at every start (`apps/server/src/config.ts`, `server.ts`).
- **The filesystem server is confined (S-3).** Its `root` is a relative folder inside the owner's own directory, `<OPENBOTS_FILES_DIR>/connectors/<user id>`. Absolute paths and `..` are refused with `INVALID_PATH`. When a session starts, the folder is created and resolved, and a symlink out of the directory is refused (`user_dir` params, `confinedFolder` and `stdioSpawnFor` in `services/connectors.ts`).
- **Postgres URLs must name a public host (S-3).** On create, on edit and again when a session starts, the URL's host is resolved and refused with `PRIVATE_HOST` when any address is loopback, private, link-local, CGNAT or otherwise non-public (the built-ins' list in `builtins/net.ts`), or when it does not resolve. A `host` or `hostaddr` in the query is refused too (`public_host` secrets, `assertPublicHost`).
- **The fetch server left the catalog (S-3).** `mcp-server-fetch` is a Python process that makes its own requests, so it cannot go through the guarded fetch. The built-in `web_fetch` does the same job behind the private-network check. A connector added from the old entry now counts as a custom stdio server, so it runs only for an admin with custom stdio on.
- **Catalog stdio servers are pre-installed from a lockfile (S-20, 8.4h).** `docker/mcp-catalog/package.json` pins the filesystem and Postgres servers at the catalog's versions, and `package-lock.json` pins every transitive dependency with its integrity hash. The server image runs `npm ci --omit=dev --ignore-scripts` on it into `/opt/openbots/mcp`, owned by root. A catalog connector starts `<OPENBOTS_MCP_DIR>/node_modules/.bin/<bin>` directly, never `npx` (`catalogLaunch` in `packages/mcp/src/catalog.ts`, called from `stdioSpawnFor`). When the binary is missing the session fails with "<name> is not installed: <path> is missing", unless `OPENBOTS_MCP_NPX_FALLBACK=true` (from source only) allows the old `npx -y package@version`. Every stdio child gets `npm_config_cache` inside its private HOME, so `npx` in a custom server or the dev fallback never needs a writable global cache (`childEnvironment` in `packages/mcp/src/stdio.ts`). No `uv` or Python is installed: the fetch server, the only Python entry, had already left the catalog (S-3).
- **The compose Postgres password is generated at install time (S-3).** `install.sh` writes a random `POSTGRES_PASSWORD` and puts the same password in `DATABASE_URL`. `docker/docker-compose.yml` passes `POSTGRES_PASSWORD` to Postgres, which refuses to create a database without one. An existing `.env` keeps the password its database already has; `.env.example` says how to change it.

### 12. Screen control lock

**What exists**

- Takeover sets `bot_screens.controlled_by_user_id`.
- A screen tool waits up to 60 seconds for the hand-back, and otherwise answers `OwnerHasScreen` (`apps/server/src/services/computer.ts:369-495`).
- One screen action at a time per Bot (`packages/computer/src/screens.ts:51-74`).
- `bash` waits for the hand back the same way and then answers `OwnerHasScreen` (`screenFree` in `apps/server/src/services/computer.ts`, `offScreen` in `packages/agent/src/tools/computer.ts`). A command can drive its Bot's screen with xdotool as easily as a screen tool.
- **A user per screen (8.4j).** Screen n's Xvfb, window manager, x11vnc and Chromium, and the agent's own `xdotool`, `import` and `feh` for it, run as `screen-n` (uid and gid 2000+n). A command runs as the bot user (uid 1000). A command for the Bot of screen n gets gid 2000+n, that screen's `DISPLAY` and `XAUTHORITY`, and nothing for any other screen. The server passes the Bot's screen number with `bash` (`screenNumber` in `services/computer.ts`). The terminal and commands without a screen get gid 1000 and reach no display (`apps/computer-agent/src/users.ts`).
- **Xauthority per screen.** Xvfb runs with `-auth` and takes only clients that present the screen's random MIT-MAGIC-COOKIE-1. The cookie is in `<runtime>/screens/screen-n/Xauthority`, mode 0640, owned by `screen-n` with group 2000+n, in a directory of mode 0710. Only the screen's processes and its own Bot's commands can read it (`xauth.ts`, `screens.ts`).
- **Private Chromium profiles.** Each profile is in `/var/lib/openbots/screens/screen-n/profile` on the agent's state volume, in a directory of mode 0700 that only `screen-n` can enter. It is no longer on the shared `/home/bot`. The server resets a profile for a new Bot with `startScreen({ fresh: true })`, since the file API cannot reach it.
- **The privileged piece.** The container starts the agent as root with only `CHOWN`, `SETUID` and `SETGID`, under `no-new-privileges`. A setuid helper would not work there, because `no-new-privileges` ignores setuid bits. As root the agent reads the token, lays out each screen's directories (`layOut`) and creates `/tmp/.X11-unix` as root's and sticky. It then sets its effective uid and gid to the bot user (`dropToBot`), keeping root as its real and saved uid, so the three capabilities stay only in its permitted set. From then on it does its own work, including the file API, as the bot user, with no more rights than a command. It starts every program through `openbots-runas` (`apps/computer-agent/native/runas.c`), a short static C helper that is not setuid. Run by the agent, whose real uid is root, the helper may set its effective uid back to 0, which restores those capabilities. It then sets every uid and gid to the target, clears the supplementary groups, checks that root is out of reach and execs. It accepts only the computer's identities: 1000:1000, 1000:(2000+n) and (2000+n):(2000+n). Run by anything else, such as a command or the terminal, its real uid is not root and it refuses. The alternative, an agent that drops privileges for each child in-process, would leave the agent holding root's capabilities in its effective set while it serves the file API. Then a symlink race in the home could make it read or write as root. The helper keeps the privileged code to a few lines that take no input but two numbers. Since 8.4m it has one more mode, `--clear-display N`, described below; it takes one number.
- **Shared downloads (8.4m, K1).** Chromium's `HOME` is the private state directory, so its own default would hide downloads from `read_file`, the terminal and the file browser. Before each start, the screen's user writes `download.default_directory` (and `savefile.default_directory`) as `/home/bot/Downloads` into the profile's `Default/Preferences`, mode 0600, keeping Chromium's other settings. The agent, as the bot user, makes `/home/bot/Downloads` the bot user's with mode 3777: setgid, so every download is in group 1000, and sticky, so one screen's user cannot remove another's files. Chromium starts under umask 002, so a download is 0664: the bot user reads and writes it, and any Bot's command reads it and, as the directory's owner, may remove or replace it. The home itself gets o+x (0751 from 0750), so the screens' users can reach the directory without listing the home. Playwright attaches with `noDefaults`, which leaves downloads to Chromium's setting; otherwise it would send them to its own temporary directory.
- **Nothing to take first (8.4m).** x11vnc listens on `<runtime>/screens/screen-n/vnc.sock` with `-unixsock`, and with `-rfbport 0 -rfbportv6 0` on no TCP port at all; before 8.4m it also held `[::1]:5900`. Only `screen-n` can create a file in that directory or connect to the socket. The agent cannot enter the directory either, so `/vnc/:n` reaches x11vnc through a relay, a few lines of node run as `screen-n` that pipe stdin and stdout to the socket (`ScreenManager.vnc`). Xvfb runs with `-nolock`, so a lock file a command makes in `/tmp` stops nothing; the abstract and filesystem sockets already keep a second server off a display. A file a command puts at `/tmp/.X11-unix/X<10+n>` would make Xvfb refuse, and the screen's user cannot remove it from the root-owned sticky directory. So before each start the agent runs `openbots-runas --clear-display n`, which as root removes exactly that name (a non-empty directory is renamed aside under a random name) and nothing else; the path is built from n. The screen counts as up only once Xvfb writes its display number to `-displayfd`, so clients never start on a socket a command made in the moment before Xvfb listens.
- **Old profiles removed (8.4m).** On every start the agent, as the bot user, deletes `/home/bot/.config/openbots/chromium`, where the profiles were before 8.4j. They held session cookies on the shared home. Migrating them was the alternative, but the agent cannot write the private directories and the screens' users cannot read the old ones; the Bots log in again once instead.
- x11vnc takes a random 8-character password per screen. It reaches x11vnc as `-passwdfile rm:` in the screen's own directory: mode 0600 and owned by `screen-n`, written by the screen's user from stdin. x11vnc deletes the file once it has read it. The password is never in argv, the environment or `ScreenInfo`. `/vnc/:n` answers x11vnc's VNC authentication with it and offers the noVNC client no authentication, because the agent token on the upgrade has already authenticated the client (`apps/computer-agent/src/rfb.ts`, `ws.ts`).
- Chromium has no DevTools port. It runs with `--remote-debugging-pipe`, so CDP goes over fds 3 and 4, which only the agent holds. Playwright reaches the pipe through a WebSocket on a 127.0.0.1 port the kernel picks. The port takes one client, and only one that sends the screen's random 32-byte secret (`apps/computer-agent/src/devtools.ts`). The bridge listened on a unix socket in 8.4c. It moved off the filesystem because the agent now runs as the same uid as the commands, so a command could replace any socket file the agent made.
- The wallpaper reaches `feh` over stdin and is written by the screen's user into the screen's directory, so no Bot can swap another Bot's wallpaper for its own text.

**Gaps (S-7)**

- The commands of every Bot run as the bot user, so the shared home (K1) keeps one owner. Giving each Bot's commands their own uid would break `chmod`, git's ownership check and ssh's key checks on files another Bot made. So one Bot's command can still signal, and kill, another Bot's commands and the terminal. It cannot trace them or read their `/proc` unless both run without a screen, because their gids differ. It also cannot read another screen's cookie or profile.
- A command can still bind the display's abstract socket, `@/tmp/.X11-unix/X<10+n>`, before that screen starts. Root cannot take back an abstract name, so Xvfb then refuses to start and the screen fails to start: a denial of service, not access, since nothing starts until Xvfb reports it listens. Turning the abstract socket off (`-nolisten local`) would be worse: clients try the abstract name first, so a command could then sit in front of every screen. Closing this needs a network namespace per screen or a display path commands cannot reach, which Xlib's clients do not support. (Before 8.4m a command could also take the lock file, the socket path or x11vnc's TCP port; with x11vnc on that port a squatter could have shown the owner a fake screen during a takeover.)
- The agent keeps `CHOWN`, `SETUID` and `SETGID` in its permitted set. Code execution inside the agent itself can take root back in the container. Such code already holds the token.
- Downloads are shared like the rest of the home (K1): every Bot, and every screen's user, can read every Bot's downloads. A Bot's command can append to a download only from the terminal's group; with its screen's group it can read, remove or replace it.
- A `bash` command or screen action already in progress continues after a takeover. A background job started before the takeover keeps running.

### 13. Private relay and paired devices

The phone app reaches a server through the relay (`apps/relay`, `apps/server/src/relay`, `packages/tunnel`; the contract is `docs/RELAY_PROTOCOL.md`). What holds:

- The relay is untrusted. A stream carries a Noise IK session (`Noise_IK_25519_ChaChaPoly_SHA256`) between the phone and the server; the relay sees the server's host id, link and stream counts and byte counts, and nothing inside. The server proves its identity to the relay with its Ed25519 instance key (a signed challenge), so nobody can register another server's host id. The phone pins the server's tunnel key from the pairing link, so a relay that lies about which host it is fails the handshake.
- A pairing is a 32 byte code, stored as a SHA-256 and compared in constant time, good for 5 minutes and spent by one conditional update. `POST /devices/pair` is rate limited per client (10 an hour) and per code (5 tries an hour). A device's key is an ordinary API key with the owner's permissions, so a paired phone is the owner. Pairing and revocation are audited.
- Revocation (`DELETE /devices/{id}`) goes in this order. First the device row is marked revoked and forgets its static key, push key and push token in one update, so whatever fails after, nothing can push to it or open a tunnel as it. Then `device.revoked` closes the device's relay streams on every API instance (and, without Redis, each open stream's device is re-checked against the database every 15 seconds; a revoked device's stream answers 401 to new requests and closes 4403 once its in-flight responses are sent, or after 5 seconds). Last its API key is deleted, and every API instance closes the `/ws`, `/computer/pty` and screen sockets opened with that key (1008 `api key revoked`), with a re-check of every open socket's key every 60 seconds as a backstop. A revocation whose key delete failed is finished by calling it again.
- A device key cannot make a long-lived credential or a new path out of the server, so a stolen phone cannot leave something behind its revocation. These answer 403 `DEVICE_KEY_NOT_ALLOWED` to a device key: `POST /api-keys`, `POST /devices/pairings`; `POST /bots/{id}/endpoints`, `POST /endpoints/{id}/rotate`, `PATCH /endpoints/{id}` sending anything but `enabled`, `match`, `template`, `responseMode` or `syncTimeoutS`; `POST /event-subscriptions`, `PATCH /event-subscriptions/{id}` sending anything but `events` or `enabled`, or `rotateSecret`; `POST /connectors`, `POST /connectors/import`, `PATCH /connectors/{id}` sending anything but `name`, `PUT /connectors/{id}/trusted`, `PUT /connectors/{id}/local`, `GET /connectors/{id}/oauth/start`, `PUT /connector-policy`; `POST /providers`, `PATCH /providers/{id}` sending anything but `name` or `smallModelId`; `PATCH /settings`; and `POST /organization/invitations` on the managed service. The first `POST /providers` of an owner with none is allowed, for headless setup, when it sends only `presetId`, `name` and `apiKey` (so no base URL, headers or `local`). Edits are refused by a list of allowed fields rather than of dangerous ones, so a field added to a schema later is refused until it is listed.
- Tunneled requests reach the server's own port on loopback. The tunnel drops `cookie`, `origin`, `sec-fetch-*`, `x-forwarded-*` and `host`, so a tunneled request is never a browser request and never a trusted-proxy request. The adapter adds `x-openbots-device` (the rate-limit key: the device id, or `remote:<address>` for a stream not paired yet) and, for a pairing, `x-openbots-device-key`; both are honoured only from loopback and only beside a secret the in-process adapter makes at each start (`x-openbots-adapter`), so neither a request from another address nor a reverse proxy or program on the same host can name a device or dodge its rate limit.
- The adapter binds a session's bearer key to its Noise device: on a known device's stream, a request whose API key is not the key of a device with the session's static key is refused 401 `DEVICE_KEY_MISMATCH` before it reaches the server, so a paired session cannot carry a key lifted from another phone. One static key may be paired with several organizations; a request is served as the device whose key it carries.
- Unknown device sessions are limited, since anyone with the server's key from a pairing link can open one. At most 2 are open per server instance, counted apart from the 8 of known devices (the next is closed 4429), and each serves one `POST /devices/pair` and closes 4400 once its answer is sent, or 30 seconds after the handshake.
- The relay holds against unauthenticated abuse: nobody is authenticated there, so what a client can spend is limited per client address as well as per host (4 open streams per host and 60 opens a minute per host from one address, 300 opens a minute from one address to any host, 50 MB a minute per address and per stream), a stream must send its first payload within 5 seconds, and a byte limit closes only the stream that passed it, never the host's link (RELAY_PROTOCOL.md 3.4).
- Presence (`GET /v1/hosts/{hostId}`) tells anyone who has a host id whether that host is online, and when it comes and goes, unless the relay sets the optional `RELAY_PRESENCE_TOKEN`, which then wants a bearer token for it. A host id is in every pairing link and is not a secret in the way a key is. The 4404 a stream gets when the host is offline stays either way.
- Push payloads are encrypted for the device (ChaCha20-Poly1305 under a per-device key made at pairing) before they leave the server; the relay and APNs see "You have a notification" and a Bot id. An APNs 410, or a 400 `BadDeviceToken` or `DeviceTokenNotForTopic`, forgets the token. An owner suspended or removed in the organization is pushed nothing.
- The server's instance key and every device's push token and key are sealed with the master key and re-sealed on rotation. Cross-organization lookups for a device by static key and a pairing by code hash go through two SECURITY DEFINER functions that return organization ids and nothing else: `openbots_device_workspaces` returns every organization with a device of that key (ids only), and `openbots_pairing_workspace` the one of a pairing. Beside them, one answers whether any device or open pairing exists (`openbots_devices_exist`), so the relay link knows whether to dial.

### 14. Standalone image and a self-hosted relay

Two deployment shapes from [MOBILE_AND_VM_PLAN.md](MOBILE_AND_VM_PLAN.md) section 8 that hold less than the compose stack does. Both are documented choices, not findings.

**The standalone image** (`docker/standalone.Dockerfile`, `deploy/`) runs the server, Postgres, Redis and the computer agent in one container, for platforms that run one container and no Docker inside it. Boundary 3 (the computer sandbox) is weaker there:

- One kernel and one network namespace. There is no sandbox network, no Docker guard and no sandbox firewall between a Bot's shell and the server.
- The Bots' shells run beside the server as another user: the agent drops every Bot process to the `bot` user as in the computer image (S-7), the server runs as its own user (uid 990, not the `bot` user's 1000) with no capabilities and `no-new-privileges`, its secrets in files only it reads, and the cookie store and the agent's files under `/data/agent` are root only.
- Postgres and Redis listen on loopback, which a Bot's shell shares. Every Postgres login over TCP needs a scram password (the socket is the superuser's only), and Redis needs a password generated at first boot and kept in a file only the `redis` user reads, so a Bot cannot read or inject queue jobs.
- The computer agent's token is removed from the environment of every program it starts, as in the computer image, so a Bot cannot drive the agent.
- A Bot's shell can reach the server's port on loopback. Every route needs a key the Bot does not have; `POST /devices/pair` needs a live pairing code and is rate limited (control 13).
- A Bot's shell can reach the VM's own network and, on a cloud VM, its metadata address. With `NET_ADMIN` (`docker run --cap-add NET_ADMIN`; a Fly Machine has it), standalone-init drops traffic to 169.254.169.254 (and fd00:ec2::254) from the Bots' uids 1000 to 2089 with an iptables owner rule, and logs whether it did. Without it, block the address in the platform (on EC2, IMDSv2 required with a hop limit of 1), and do not give the VM a role it does not need.
- `OPENBOTS_SANDBOX_EGRESS_PROXY` is advisory in the standalone image: it sets `HTTP_PROXY` and `HTTPS_PROXY` for the Bots' programs, and nothing enforces it, since there is no sandbox firewall.
- On Fly, the Machine's private network is reachable from the Bots' shells: other apps in the organization (`<app>.internal`) and, when present, the Machines API socket `/.fly/api`. Run OpenBots in a Fly organization of its own.
- The server's environment holds no secret: `DATABASE_URL`, `REDIS_URL` and the other secrets reach it as files under `/run/openbots`, and `POSTGRES_PASSWORD` and `OPENBOTS_REDIS_PASSWORD` are removed before it starts.
- Under memory pressure the kernel ends the Bots' processes first (`oom_score_adj` +500 for the computer agent's tree, -500 for the server, Postgres and Redis where allowed). The process count is bounded only by `docker run --pids-limit`.
- One volume serves one container: `volume-lock` holds `flock` on `/data/.lock`, and a second container stops before Postgres starts. With an existing database, a missing master key or password stops the boot instead of being generated again.
- On a platform that publishes the port at once (Railway, Render), pair from the terminal before making the service public, so nobody can create the owner through the web wizard first; the image sets `OPENBOTS_SETUP_PAIRING_ONLY=1`, which refuses owner creation from the wizard.
- It is single tenant: it refuses `OPENBOTS_DEPLOYMENT=managed` (V6).

The README's "Run OpenBots 24/7 on a VM" and `deploy/README.md` say this in plain words and name the compose stack as the hardened path.

**A self-hosted relay** (the compose `relay` profile, `docker/docker-compose.relay.yml`) is the same untrusted relay as control 13, run by the owner. Its container is read only, holds no capability and no secret, and writes nothing to disk. Its port is published on loopback by default, for a TLS terminator on the same host or a tunnel on the stack's network, and it trusts the last `X-Forwarded-For` hop (`RELAY_TRUST_PROXY=true`) for its rate limits; publishing the port on every interface without a proxy in front lets a client choose the address its limits key on, so `docker/docker-compose.relay.yml` says to set `OPENBOTS_RELAY_TRUST_PROXY=false` then. It carries no push, since it has no APNs key. Running it moves nothing inside the Noise session into its reach: it sees what the hosted relay sees, and now the owner holds those logs.

## Organizations on the managed service (plan 21)

- Tenancy: every request works in one organization, resolved from the session or the API key, and the caller must be an unsuspended member of it; a session whose organization the user left gets 403 `NO_ORGANIZATION` (`middleware/auth.ts`). Rows are read by organization and owner; webhook ingress finds the organization through the endpoint and names the Bot by id; realtime account events carry the organization; outbound events go to the event's organization only.
- Roles: only an owner touches an owner, the last owner stays, and nobody suspends or removes themselves (`ee/server/src/organizations.ts`, under the organization's lock). Admins never reach members' Bots or per-user data, and their connector trust and local marks reach only their own connectors.
- Invitations: one address each, 7 days, accepted once by that verified address, revocable, 100 pending and 30 sent an hour per organization. Invite-only sign-up needs the invitation from the link, for the same address. better-auth's `/api/auth/organization/*` endpoints are not served over HTTP.
- Email verification: a managed sign-up takes the email first and the password only after the 6-digit code sent to it, so a second sign-up for the same address cannot set a credential the inbox owner then confirms. The code is bound to its request (a random id in an HttpOnly cookie), single use, 10 minutes, stored as an HMAC and compared in constant time. Sign-ups and code tries are limited per IP first (20 and 50 an hour). Sends are limited per address (10 an hour, 20 a day) only for requests that passed the policy checks, before anything is made. Each code dies after 5 tries, and an address that fails 15 times in a rolling hour, across its codes, cannot verify until that hour clears; a correct code never counts. Worst case for guessing: 20 codes a day times 5 tries is 100 guesses a day, about 3,000 a month against a million codes, so about a 0.3% chance a month of guessing one address. Worst case for lockout: failed tries lock an address for at most an hour after the 15th; an attacker who spends an address's sends blocks new codes for it for up to a day. Confirming an address left with an unconfirmed account from before this flow deletes that account and everything tied to it (linked identities, sessions, memberships, invitations, API keys) in the same transaction that creates the confirmed one. An address with an account gets a notice instead of a code, with the same answer to the requester. No unauthenticated request deletes or replaces an account. The core refuses an unconfirmed account's requests and API keys. Codes, emailed links and tokens never reach a log, except codes on a development server that sets `OPENBOTS_DEV_LOG_EMAIL_LINKS` (refused with `NODE_ENV=production`); request logs redact invitation ids.
- OAuth sign-up from an invite: the invite rides through GitHub or Google in a signed, HttpOnly, SameSite=Lax cookie that lasts 10 minutes, never in the OAuth state. The new account joins only when the invitation is pending and for the address the provider verified, and only once.
- Shared server: custom stdio connectors and local endpoints are off unless the operator turns them on (`OPENBOTS_CUSTOM_STDIO`, `OPENBOTS_LOCAL_ENDPOINTS`); organization limits stay under the operator's ceiling (400 `ABOVE_PLAN_LIMIT`); organization creation (5 an hour per person) and invitations are rate limited.
- Stdio connectors: each runs in its owner's computer for that organization (`OPENBOTS_STDIO_RUNNER=computer`, the managed default; see control 11), never on the shared server, so organizations, and the members of one, share no process or files. The server refuses `host` there unless the operator sets `OPENBOTS_ALLOW_HOST_STDIO=1`, and warns at every start when they do.
- Row-level security, the second layer: under the services' own filters, Postgres keeps each organization's rows to it (`drizzle/0023_row_level_security.sql`, `db/scope.ts`, plan 21.9). The app works as `openbots_app`, a role that owns nothing and does not bypass RLS; every table with `workspace_id`, and `workspaces`, has forced RLS with one policy on `app.workspace_id`, which each transaction sets for the organization of its request, job, socket or webhook; with it unset nothing is seen or written. The paths that are not one organization's work are each narrow and listed in one place, `db/scope.ts`: the organization directory as `openbots_auth` (account tables, memberships, invitations and API keys only), work for every organization run in each one's scope in turn, and eight SECURITY DEFINER lookups that return ids or a yes or no (organizations, organizations with a Routine due, a webhook path's organization, a connector's for its OAuth callback, a paired device's organizations by its static key, a pairing's by its code hash, whether any device or open pairing exists, and the organizations with a connection to a GitHub App installation, S-34). With `OPENBOTS_DB_APP_PASSWORD` the app logs in as `openbots_app`; without it, it connects as the owner and switches role in each transaction, which holds every query the app makes to the same policies but would not stop a statement that resets the role, so installs set it (install.sh and the Mac app generate it).

**Tests:** `apps/server/src/routes/org-isolation.test.ts`, `apps/server/src/db/rls.test.ts`, `apps/server/src/auth.test.ts`, `apps/server/src/ws/gateway.test.ts`, `ee/server/src/organizations.test.ts`, `ee/server/src/verification.test.ts`.

## Coding agents on the computer (plan 22)

Reviewed on 2026-11-05 against the Phase 1, 2 and 3 code on `feat/coding-agents`, which runs Claude Code, Codex and pi on the Bot's computer and connects them to GitHub (plan 22, Phase 2 in 22.12, Phase 3 in 22.13). The review read the code and ran its tests. On 2026-11-06 the computer agent's root-only suites (`layOut`, `runas`, the privileges and the screens) also passed inside the built image on linux/arm64, and the uid separation held there (TRACEABILITY.md, "What the unit tests cannot show"); the rest of these items still need the hand checks in README, "Checking the container hardening", steps 14 to 25. A coding agent adds two things to protect: the owner's vendor sign-in, which is the same class of secret as the browser cookie store, and the owner's GitHub access, which can push. Phase 2 adds a third: the install's GitHub App, whose installations can reach every repository of an organization.

- **A user of its own (S-22).** Every coding agent and every vendor login runs as `coder` (uid 1800, group `coders`), through `runas`, which allows that user no other group (`apps/computer-agent/src/users.ts`, `native/runas.c`). What it can read:
  - Its own config directories, `/var/lib/openbots/coders/{claude,codex,pi}`, and its `HOME`, `/var/lib/openbots/coders/home`: yes, each coder 0700 on the root-only state volume. The bot user cannot enter them, so a Bot's `bash` cannot read the owner's Claude sign-in, and `claude` run as bot finds no credentials.
  - The cookie store (`/var/lib/openbots/cookies`, cookies 0700): no.
  - The Bot's home: yes, through the group, for the repositories. `/home/bot/repos` is bot:coders 2775 with setgid, sessions run under `umask 002`, and clones are made with `core.sharedRepository=group`, so both users read and write every clone and worktree. The rest of the home is enterable but not listable by other users (mode o+x only), so the coder user reaches a file there only when it knows the name and the file's mode lets others read it.
  - Other screens' state and the agent's `/proc`: no, as for the bot user (S-7).
  - The session directories under `<runtimeDir>/coders` are root:coders 1730: a session's own directory can be entered by its processes, nobody can list the parent, and the bot user's ordinary commands cannot enter it.
  - Tests: `apps/computer-agent/src/privileges.test.ts` "gives each screen directories that only its user, and for the cookie its Bot's group, may enter" (the coder directories 0700 1800:1800, the sessions directory 1730 0:1800), "runs a coding agent as the coder user, and the owner's session command with the coders group (I2)", `shareRepos (I2)` "makes the repositories directory, setgid in the group it is given"; `ws.test.ts` "opens the coder user's shell, under umask 002, with the agents' config directories (I15)".
- **Credentials never on disk (S-23).** Vendor sign-ins stay in the agent's config directory on the computer; no API returns them and `coder_accounts` holds only the label (`apps/server/src/services/coder-login.ts`, `coder-login-driver.ts`). Claude Code signs in with `claude auth login --claudeai`, whose credentials land in `$CLAUDE_CONFIG_DIR/.credentials.json` and which prints nothing secret; `claude setup-token`, which prints a one year token to its terminal, is not used, so no vendor token crosses the PTY to the server. The code the owner pastes goes to the login over the control channel, is never stored and is cut out of error text. Git tokens never touch the computer's disk: git's helper (`git-credential-helper.ts`) asks over the session's own unix socket (`credential.sock`, 0660, group coders) with a per-process secret, 32 random bytes the agent mints at start into `OPENBOTS_CODER_SESSION` and compares in constant time. It is not the server's session id, which the Bot's shell can learn. The token lives in the helper for the length of one git call and in one `credential` frame. There is no loopback HTTP credential endpoint. The server's check fails closed (`services/git-credentials.ts`): only `github.com`, only a request that names a path, only the session's own repository (or the runner's own operation's), and `push` only when approved. The helper is set through the environment after every config file, so a repository's own config cannot swap it. Tests: `coder.test.ts` "refuses the server's session id, or any other secret, without asking the server", "passes on a refusal, and refuses when the server is slow or the session ends", "has no POST /git/credential any more: without the token it is a 401"; `git-credential-helper.test.ts` "prints nothing for a refusal, no secret or socket, a missing agent or an answer git could misread"; `git-credentials-scope.test.ts` "denies a request without a path", "denies another repository", "denies a process that is not a session of a repository", "denies hosts other than github.com, the API host included", "still gates the push".
- **Same uid, concurrent sessions (S-24).** Every session runs as the same coder uid, and a process can read the environment of another process of its own uid (`/proc/<pid>/environ`). So a process of one session can take the secret of another session running at the same time, and then ask that session's socket for its repository's credential, a push credential included while that session is push-approved. Both sessions are the same owner's, on the same computer, and each is one of their own Bots, so this crosses no account; it does cross the per-session repository scope. The server's own git no longer shares that uid (S-30), so what is left is coding sessions running at the same time. Per-session uids would close it later (plan 22.13).
- **Shared App device credentials (S-25, S-29, S-32).** The default coding-repository device connection (`kind: device`) stores a sealed GitHub App **user** token, not a repository-narrowed installation token. Listing and sync intersect the user's active installations of the configured App and their own repository access, across accounts; write requires both installation contents-write and user push permission. An isolated runner clones/fetches, and a sandbox receives no token until its approved push for the exact repository path, using the existing unnarrowed-token gate. After exposure for approved push, that token can reach other repositories selected for the App: this residual risk is the same class as a PAT, bounded by the App's selection and user permissions. PRs act as that user. Codes and rotating tokens are encrypted under the existing master key and workspace RLS; owner/row locks serialize polling, reconnect and refresh across processes; fixed GitHub endpoints, no redirects and sanitized errors prevent credential disclosure. No client secret, signing key, callback or public HTTPS is needed. This is separate from both the MCP connector and server-managed App installation tokens; configured/manifest Apps keep the stronger narrowing below. Device connections have no automatic centralized webhook delivery. Tests: `routes/git-device.test.ts`, `features/repos/repos.test.tsx`; real GitHub clone/approved-push/PR verification remains manual, [GITHUB_REPOSITORIES.md](GITHUB_REPOSITORIES.md).
- **The owner's token on the computer (S-25).** Through a server-managed GitHub App connection the token served is an installation token for the session's one repository, `contents: read` until the push is approved, and good for an hour at most (S-29). Through a token connection, or the GitHub connector with no connection, the token is the owner's own, which GitHub cannot narrow: a session gets it only for its approved push (S-32), and a process that catches it then can use it for whatever that token reaches until it is revoked. Owners on that path should give OpenBots a fine-grained token limited to the repositories they add, or connect the App.
- **The classifier is a soft control (S-26).** `classify` reads a command as the shell would and decides which action class it is, and so whether the owner is asked. A command it misreads may run without asking. It is not the boundary. The hard controls are: the coder uid's filesystem permissions (S-22); the credential helper's repository scope and push gate (S-23); `git push`, `WebFetch` and `WebSearch` disallowed at launch, and the read tools left to Claude Code's own working-directory check rather than pre-allowed unscoped; the worktree, so a bad session's reach is one branch; and the computer's sandbox firewall and egress proxy, the same as for every Bot. With a token connection or the connector, a session gets no fetch credential at all (S-32). Not guarded: pi still reads `$PI_CODING_AGENT_DIR/models.json`, where a session could point a provider at another endpoint, and the next pi session with a key for it would send the key there (the egress proxy, where it is on, still limits where it can go). Claude Code's own settings in `CLAUDE_CONFIG_DIR` are likewise the coder user's, and the launch passes no flag that ignores them (`coder-adapters/claude.ts`). Tests: `codex.test.ts` "launches app-server with the sandbox, the approval policy and the provider as overrides" (every override, the network off, and no `--ignore-user-config`), "resumes a vendor thread, and starts a new one when it is gone"; `pi.test.ts` "launches pi headless with the OpenBots extension and its own session id" (`--no-extensions`, `-e`, `--no-mcp`, `--no-approve`, `--tools`).
- **A refused key is never switched to a plan (S-41).** When the provider refuses an `api_key` account's key (a 401, "unauthorized" or the adapter's not signed in text, read only from the CLI's own output: the result's error, error events and stderr, never the model's summary), the session fails with "The <provider> API key for <agent> was rejected. Check it under Settings > Models.", the account keeps `auth_kind` `api_key` with that `last_error`, and no sign-in widget is posted (`finish` in `services/coder-runner.ts`). The card reads the error as a key problem (`lastErrorKind`) and links to Settings > Models. A key a CLI holds itself (Codex logged in with a key, or a key in pi's own store) is recorded by Check as `api_key` with no provider and no key text. Tests: `coder-runner.test.ts` "fails a Codex api_key session whose key is refused, without a sign-in", "fails a pi api_key session whose key is refused, and marks a pi sign-in that is missing", "never reads a sign-in from the model's own summary"; `coder-accounts.test.ts` "says which accounts need a sign-in, and what their last error is about", "stores pi's own API key as api_key, with no provider and no key text", "stores Codex's API key login as api_key without the status line"; `apps/web/src/features/coders/coders.test.tsx` "says a rejected key with a link to Settings > Models, and other errors as they are".
- **What the safety-net commit takes (S-42).** After an `edit` or `pr` session the runner commits what the agent left uncommitted, so the branch, its diff and a PR carry it (`commitLeftovers`, `services/session-git.ts`). - **Reset computer (S-43).** A reset removes the computer's home volume, and with the owner's choice the state volume with the cookie store and the coding agents' sign-ins (`services/computer-reset.ts`, `destroyComputer` in `services/computer.ts`, plan 22.14). - **Session transcripts (S-44).** The drawer's chat (CA15) reads `coding_session_events`, which has forced row-level security with `organization_isolation` like `coding_sessions` (`drizzle/0035_coding_session_events.sql`); `GET /coding-sessions/{id}/events` and `POST /coding-sessions/{id}/turns` answer only the session's owner (404 otherwise), and `coding_session.events` and `coding_session.updated` go only to the owner's sockets in that organization.
